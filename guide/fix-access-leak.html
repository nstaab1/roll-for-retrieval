The Access Leak

The store holds the DM's documents beside the nights, and your search returns whatever sits nearest the question, to whoever asks. You ask as a player and get the DM's secret back. Then you write one filter, inside the query, and ask one question as two members to watch the same code give two answers.

Done when

  • npm test -- fix-access-leak passes
  • the Strahd question, asked as katie, no longer cites barovia-strahd-plan
  • the Blinsky question answered for katie and not for millie

1 Predict where the filter goes

Every chunk carries a visibility, such as barovia/party or barovia/dm, and members.json says which ones each member may see. Nothing reads either yet. Before you see what that costs, pick where a filter would go.

2 Ask as a player

katie plays at both tables and runs neither. Ask what Strahd has planned: 

npm run ask -- --user katie "What does Strahd plan for the party after the festival?"

Read the chunks under the answer. The first is likely barovia-strahd-plan, with visibility barovia/dm: the DM's notes for next night. The answer tells a player about the dinner at the castle, which is the secret the party doesn't know yet.

No leak at your values? Ask the backup instead. A Toe Wittine DM document answers it, and a leaking answer names Hazel. 
npm run ask -- --user katie "Who does Elder Briar write to every winter?"

3 Run the access tests 

npm test -- fix-access-leak

Every test fails, on the secret or on a chunk the asker may not see. Open test/fix-access-leak/placement.test.ts. Its store has 6 DM chunks nearest the question, and it tries the two places a filter doesn't work:

  • After search. Search returns its 8 nearest, and the DM's chunks take 6 of those places. Drop them and a player keeps 2 of their 8. Your reranker has also read the DM's text by then. On the eval's hosted reranker swap, so has cohere/rerank-v3.5, on someone else's servers.
  • On the answer. The prompt already holds the secret, so the model has read it. It can word the secret any way it likes, and a filter on its answer can't know what to look for.

every-member.test.ts asks as every member of members.json, at both campaigns, and as a member the file doesn't know.

Open src/access.ts. ask already calls searchVisible with the asker's visibilities, and until now it ran your Act 3 search. The filter is one line in your Act 3 query.

Why each numbered part is there. Point at one to see its lines.
(1) Inside the query, before top-k. WHERE runs before ORDER BY and LIMIT, so the asker gets the k nearest chunks they may see, all k of them. A DM chunk never leaves the store, so neither the reranker nor the model reads it.
(2) The filter names no visibility. allowed comes from members.json through ask. An empty list matches nothing, so a member the file doesn't know gets no chunks at all.

5 Ask again 

npm test -- fix-access-leak
npm run ask -- --user katie "What does Strahd plan for the party after the festival?"

The tests pass. The answer is "I don't know", or something from the nights, and no chunk under it is barovia/dm. The DM's plan never left the store.

6 Same filter, different rows

millie plays at Toe Wittine's table only. Blinsky's shop is in Barovia. Ask as millie: 

npm run ask -- --user millie "What does Blinsky sell?"

No Barovia chunk comes back, so the answer is "I don't know". Now ask as katie, who sits at both tables: 

npm run ask -- --user katie "What does Blinsky sell?"

This time the chunks under the answer come from Barovia nights, and at most values the answer is toys. The same question, the same filter and the same code gave two answers, because millie and katie are different rows in members.json. A second campaign, or your company's second team, is more rows in that file, never more code.

Out of time, or the tests won't pass? Run npm run catch-up -- fix-access-leak. It brings the filter onto your branch and leaves your choices.ts as it is.
