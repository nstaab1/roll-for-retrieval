Roll for Retrieval · Act 3

Embed, Index and Search

A chunk is text, and you can't search text by what it means. You embed every chunk into a vector, store the vectors in Postgres beside the night, time and visibility each chunk carries, and write the search that brings back the nearest ones. Then you read what comes back, mistakes included.

1 Add embedChunks

Open src/embed.ts. An embedding model turns a text into a vector, a long list of numbers, so that texts that mean similar things get vectors that point in similar directions. The shipped client in src/hosted.ts makes the call. You send it the chunks in batches of 256.

1  const embedded: EmbeddedChunk[] = [];2  // (1) One request per batch of chunks, not one per chunk.3  for (let i = 0; i < chunks.length; i += embedBatchSize) {4    const batch = chunks.slice(i, i + embedBatchSize);5    // (2) The shipped client: one vector per text, in the order sent.6    const vectors = await embed(7      batch.map((chunk) => chunk.text),8      { model },9    );10    // (3) Each vector rides with its chunk.11    for (const [j, chunk] of batch.entries()) {12      embedded.push({ ...chunk, embedding: vectors[j] });13    }14  }15  return embedded;
Why each numbered part is there. Point at one to see its lines.
(1) Batches, not one call per chunk. Sending the 1,021 chunks one at a time would take 1,021 round trips. A request can only carry so much, so you can't send them all in one either.
(2) The shipped client. embed picks the provider from your key, returns one vector per text in the order sent, and writes the call to the cost log. The last hour reads cost per question from that log.
(3) The vector rides with its chunk. vectors[j] belongs to batch[j], and the spread keeps the night, times, document and visibility beside it. Get the pairing off by one and every chunk is filed under its neighbour's meaning.

2 Add indexChunks

Open src/store.ts. The vector store is PGlite, which is Postgres running inside Node, with the pgvector extension. The chunks table is already there. It has a column for everything a chunk carries, visibility included, and an embedding column of pgvector's vector type. You write the insert.

Why each numbered part is there. Point at one to see its lines.
(4) One transaction. If an insert fails halfway, no rows land, so you never search a half-built index. Postgres also commits once, not once a row.
(5) A column for everything. Act 4 cites the night and start_ms, or the document, and the last hour filters on visibility. A field left out here is gone for every later step.

3 Add search

Open src/search.ts. A search embeds the question, then asks Postgres for the rows whose vectors are nearest it. <=> is pgvector's cosine distance: 0 when two vectors point the same way, and bigger the further apart they point.

In src/search.ts, replace this line with the code below it:

src/search.ts · search 
1  // (6) Embed the question with the model that built the index.2  const [vector] = await embed([question], { model: store.settings.model });3  // (7) Nearest first, and only the first k.4  const { rows } = await store.db.query<Hit>(5    `SELECT night, start_ms, end_ms, document, campaign, visibility, text,6            embedding <=> $1 AS distance7     FROM chunks8     ORDER BY distance9     LIMIT $2`,10    [toVector(vector), k],11  );12  return rows;
Why each numbered part is there. Point at one to see its lines.
(6) The index's model, not the newest one. Each embedding model places texts in a space of its own, so a distance only means something between two vectors from the same model. That's why the index records the model it was built with.
(7) Nearest first, then stop at k. ORDER BY distance puts the closest meaning first and LIMIT keeps k. Nothing in this query reads visibility yet, so any chunk can come back to anyone.

4 Choose your k

Open src/choices.ts and fill in RETRIEVAL_K, the number of chunks a search returns. In Act 4 the reranker reads all k and keeps the best few for the prompt.

  • A small k is fast and cheap to rerank, but the chunk that answers the question may sit just past the cut.
  • A big k gives the reranker more chances to find that chunk, and costs a reranker pass on every extra one.

6 Build your index

The act 3 checkpoint ships an index at index/shipped.tar.gz, built at chunk size 600, overlap 1, with openai/text-embedding-3-small. If your chunk values from Act 2 are the same, skip this step. If not, build one at yours: 

npm run ingest

It prints the nights it found, grouped by campaign, then loads the documents. It runs your cleaning and chunker, embeds every chunk, and saves index/yours.tar.gz with the values it was built at. At the shipped values that's 1,021 chunks for about $0.003. From then on, npm run search searches yours.

7 Read what comes back

Ask the store a question and read the raw result, with no reranker and no answer yet: 

npm run search -- "How did the party destroy the windmill?"

The first line says which index you searched and what it was built at. Each hit gives its distance, then its night and the moment in it, or its document, then its visibility.

The party burned the windmill in barovia-2026-01-07. At 0:12:11 the DM says The windmill starts to take off in flames. Now read down your list. Which nights do the nearest hits come from?

Look for hits from other nights near the top. Distance measures how alike the words and the topic are, not whether a chunk answers the question. That's the job Act 4 gives the reranker, which reads the question and each chunk together and sorts your k again. The last hour comes back to this question to see how far that gets you.
